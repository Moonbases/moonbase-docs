---
title: Checkout Guards
description: Stop a checkout in the browser until a plugin's requirements are met.
---

A checkout guard is an async check that runs when a shopper clicks to pay. If any guard returns `false` (or throws), the checkout doesn't start and the shopper sees "Checkout was blocked. Review the requirements and try again."

<Callout type="info" title="Guard entry points">
  The 2.0 storefront runs the guards in `app/features/purchases/api.ts`, before it calls the checkout API:

  - `startCheckout` → `POST /api/purchase/cart/checkout` (signed-in shoppers)
  - `startGuestCheckout` → `POST /api/purchase/guest/checkout` (guest checkout)

  Wholesale orders from the reseller page don't run guards. If your own UI starts a checkout, call `runCheckoutGuards` from `@/lib/plugins/guards` first.
</Callout>

<Tabs items={['Guard context', 'Example']} defaultIndex={0}>
  <Tab>
    ```ts
    type CheckoutGuardContext = {
      type: 'cart' | 'product';
      items?: Array<{ productId: string; plan?: string; quantity?: number }>;
      productId?: string;
      plan?: string;
      paymentMethod?: string;
    };
    ```

    Every 2.0 checkout is a cart checkout, so the storefront always sends `type: 'cart'`, the cart `items` (`plan` is `daily`, `monthly`, `yearly` or `lifetime`) and the chosen `paymentMethod` (`stripe`, `paypal` or `coinbase`). `type: 'product'`, `productId` and `plan` remain in the type for 1.x code but aren't sent.
  </Tab>
  <Tab>
    ```tsx
    const plugin: FrontendPlugin = {
      name: 'license-guard',
      bootstrap: (ctx) => {
        return ctx.checkout.registerGuard(async (context) => {
          const items = context?.items ?? [];
          if (items.length === 0) return true;
          const response = await ctx.api.post('/api/plugins/license/check', { items });
          return response.ok;
        });
      }
    };
    ```

    Return the cleanup from `registerGuard` so the guard is removed with the plugin.
  </Tab>
</Tabs>

<Callout type="warn" title="Guards don't enforce anything">
  Guards run in the shopper's browser and can be skipped by calling the API directly. Enforce the same rule in the backend, before the checkout route runs: see [Extending checkout](/docs/plugin/backend/routes#extending-checkout). Guest shoppers have no session, so `ctx.api` calls from a guard reach your API route without a `Token` header.
</Callout>

## Outcome

- Guards run one after another in registration order. The first that returns `false` or throws stops the checkout (an error is logged with `console.warn`).
- A guard can show its own UI first, for example by opening a modal in the `global` slot and resolving once the shopper has finished.
