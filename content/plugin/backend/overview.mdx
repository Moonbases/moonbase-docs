title: Backend Runtime Overview
description: How the API finds, loads and runs backend plugins.
---

The API loads backend plugins once, at startup, after it has connected to MongoDB and loaded the store settings, and before it starts listening. Plugins are plain JavaScript files read from disk, so you can add one without rebuilding the API.

## Plugin locations
The loader uses the first of these folders that exists:

<Steps>
  <Step>The folder in `PLUGINS_DIR` (in `api/.env`), resolved from the API's working directory. If the folder doesn't exist, the loader falls through to the next locations.</Step>
  <Step>`plugins` in the API's working directory. The start scripts run the API from `api/`, so this is `api/plugins` in the release package.</Step>
  <Step>`apps/api/plugins` under the working directory (running from the root of a source checkout).</Step>
  <Step>A `plugins` folder next to the compiled API (internal fallback).</Step>
</Steps>

<Callout type="info" title="Recommended location">
  Put plugins in `api/plugins` (`apps/api/plugins` in a source checkout). Set `PLUGINS_DIR` only when you keep plugins outside the install, for example `PLUGINS_DIR=/srv/moonbase-plugins`.
</Callout>

The API logs one line per plugin it loads (`Loaded plugin <name> from <file>`), skips or fails to load. With nothing to load it logs `No plugins directory found.` or `No plugins found in plugins directory.`

## Supported files
<Cards>
  <Card title="File types" description="`.js` and `.cjs` (CommonJS, loaded with require) or `.mjs` (ES module, loaded with import)" />
  <Card title="Folder entry" description="A folder with `index.js`, `index.cjs` or `index.mjs`" />
  <Card title="Ignored entries" description="Names starting with `_` or `.` are skipped, and so is any other file type" />
</Cards>

<Callout type="info" title="Load order">
  Plugins load one after another in alphabetical order of their path. A plugin's `register` may be `async`: the next plugin loads only once it has finished.
</Callout>

## Plugin shape
<Tabs items={['Object export', 'Function export', 'ES module']} defaultIndex={0}>
  <Tab>
    ```js
    // api/plugins/my-plugin.js
    module.exports = {
      name: 'my-plugin',
      enabled: true,
      version: '0.1.0',
      register(ctx) {
        ctx.logger.info('plugin loaded');
      }
    };
    ```
  </Tab>
  <Tab>
    ```js
    // api/plugins/my-plugin.js
    module.exports = function register(ctx) {
      ctx.logger.info('plugin loaded');
    };
    ```
  </Tab>
  <Tab>
    ```js
    // api/plugins/my-plugin.mjs
    export default {
      name: 'my-plugin',
      async register(ctx) {
        ctx.logger.info('plugin loaded');
      }
    };
    ```
  </Tab>
</Tabs>

<Callout type="warn" title="Errors while loading">
  If `register` throws, the API logs `Failed to load plugin <file>: <message>` and carries on without it. Anything the plugin registered before the error (routes, hooks, patches) stays in place, so validate your setup first and register routes last. A file without `register`, `init` or a function export is skipped with a warning.
</Callout>

## Where plugins sit in the request pipeline

Plugins load in the middle of the API's setup, which decides what a route sees:

<Steps>
  <Step>Client IP resolution, request context, request logging, cookies, compression and security headers.</Step>
  <Step>Payment provider webhooks (`/api/purchase/webhook`, `/webhook/coinbase`, `/webhook/paypal`) with their raw bodies.</Step>
  <Step>**Plugins load.** Routes added to `ctx.app` now run before every other API route, and before any body parser.</Step>
  <Step>`express.urlencoded()` and `express.json()`.</Step>
  <Step>The v2 API (`/api/v2`), then the `$`-key filter, then the v1 routers: `/api` (`ctx.routers.api`), `/api/dashboard` (`ctx.routers.dashboard`) and `/api/purchase` (`ctx.routers.purchase`).</Step>
  <Step>`onRoutesReady` callbacks. Routes added to `ctx.app` here run after the core routes.</Step>
  <Step>The not-found handler and the error handler.</Step>
</Steps>

[Routes and Security](/docs/plugin/backend/routes) explains how to pick the right place for a route.

## Dependencies

A plugin can `require` Node's built-in modules and any package it can resolve from its own folder. The release package ships the API as a single compiled file. Express, Mongoose and the API's other libraries are built into that file, so they aren't installed in `api/node_modules`.

- **Express:** use `ctx.express` (for example `ctx.express.json()` or `ctx.express.Router()`).
- **Mongoose:** use `ctx.mongoose`, the API's connected instance. A separately installed copy isn't connected to the database, so its queries never finish. This also applies to a source checkout run with `pnpm start`, where the API is bundled too.
- **Other packages** (for example `axios`): make the plugin a folder with its own `package.json` and run `npm install` inside it. Don't install them into `api/` itself, because the installer runs `npm ci` there and removes packages it doesn't know about.
